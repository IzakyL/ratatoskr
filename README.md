# Ratatoskr

English | [简体中文](README.zh-CN.md)

A minimal Yggdrasil authentication service and skin service, running on Cloudflare
Workers and intended for use with
[authlib-injector](https://github.com/yushijinhun/authlib-injector).

- Workers for the API, D1 for accounts, characters and tokens, KV for skin images
  and join records.
- Skins are content-addressed by SHA-256, which deduplicates identical uploads and
  allows the texture URL to be cached indefinitely.
- Texture properties are signed with RSA (`SHA1withRSA`); Minecraft servers verify
  this signature before trusting a skin URL. It is required by the protocol.
- Passwords are generated by the server and cannot be chosen by the user. See
  [Passwords](#passwords).
- Registration requires a single-use invite code. See [Invites](#invites).
- Optional [bridge mode](#bridge-mode): players from Mojang, LittleSkin or any
  other Yggdrasil service can join the same Minecraft server, with names protected
  across services.
- Includes a small web interface for registration, sign-in and skin management,
  available in English and Chinese. The first account is the administrator, and sees
  an [administration view](#administration) there.

## Deployment

```bash
npm install
npx wrangler login
npm run setup
```

`setup` creates the D1 database and the KV namespace, writes their ids back into
`wrangler.jsonc`, applies the migrations, generates an RSA key and stores it as the
`SIGNING_KEY` secret, deploys, and asks for the email address and character name of
the administrator, whose account it then creates. The administrator's password is
printed once. It is safe to run `setup` more than once: existing resources are
reused rather than recreated, and a second administrator is never created.

Sign in with that account to reach the administration view, where invite codes are
issued.

Subsequent deployments:

```bash
npm run deploy
```

### Custom domain

Add the hostname to `wrangler.jsonc` and deploy again. The domain must be on the
same Cloudflare account:

```jsonc
"routes": [{ "pattern": "auth.example.com", "custom_domain": true }]
```

Nothing else has to change. `PUBLIC_URL` can stay empty: the metadata document takes
its origin — and therefore the entry it puts in `skinDomains`, and the texture URLs it
signs — from the host of the incoming request, so the Worker answers correctly on
`workers.dev` and on the custom domain alike.

Set `PUBLIC_URL` when the origin must be pinned regardless of which host was asked
for: behind a reverse proxy, or to keep the `workers.dev` hostname out of texture URLs
once the real domain is live.

```jsonc
"vars": { "PUBLIC_URL": "https://auth.example.com" }
```

Moving to a new domain is safe — texture signatures are produced per request, not
stored — but players have to update the authentication server address in their
launcher, and servers the `-javaagent` argument.

## Using the service

In a launcher, add the following address as an external authentication server:

```
https://<your-worker-url>/api/yggdrasil
```

On the Minecraft server, attach authlib-injector to the JVM:

```bash
java -javaagent:authlib-injector.jar=https://<your-worker-url>/api/yggdrasil -jar paper.jar
```

Two settings in `server.properties` matter:

- `online-mode=true` — authentication is only enforced when this is on.
- `enforce-secure-profile=false` — required, because chat signing depends on
  Mojang's `/minecraftservices` certificate endpoints, which this service does not
  implement.

## Endpoints

The Yggdrasil API lives under `/api/yggdrasil`:

| Method | Path | Description |
| --- | --- | --- |
| GET | `/api/yggdrasil` | Metadata document; the URL clients are pointed at |
| POST | `/api/yggdrasil/authserver/authenticate` | Sign in with an email address or a character name |
| POST | `/api/yggdrasil/authserver/refresh` | Issue a new token and invalidate the previous one |
| POST | `/api/yggdrasil/authserver/validate` | Check whether a token is still valid |
| POST | `/api/yggdrasil/authserver/invalidate` | Invalidate a single token |
| POST | `/api/yggdrasil/authserver/signout` | Invalidate every token held by an account |
| POST | `/api/yggdrasil/sessionserver/session/minecraft/join` | Client-side join request |
| GET | `/api/yggdrasil/sessionserver/session/minecraft/hasJoined` | Server-side verification; returns a signed character |
| GET | `/api/yggdrasil/sessionserver/session/minecraft/profile/{uuid}` | Look up a character; `?unsigned=false` to include a signature |
| POST | `/api/yggdrasil/api/profiles/minecraft` | Resolve character names to UUIDs, up to 10 per request |
| PUT | `/api/yggdrasil/api/user/profile/{uuid}/{skin\|cape}` | Upload a texture (bearer token, `multipart/form-data`) |
| DELETE | `/api/yggdrasil/api/user/profile/{uuid}/{skin\|cape}` | Remove a texture |

Outside the Yggdrasil namespace:

| Method | Path | Description |
| --- | --- | --- |
| POST | `/api/register` | Register an account; spends a single-use invite code, returns the generated password once |
| GET | `/textures/{sha256}` | Fetch a texture |
| GET | `/` | Web interface |

Administration, all requiring the administrator's access token as a bearer token:

| Method | Path | Description |
| --- | --- | --- |
| GET | `/api/admin/state` | Every account, invite code and bridged player, in one document |
| POST | `/api/admin/invites` | Issue invite codes; `{ count?, note? }`, at most 20 at a time |
| DELETE | `/api/admin/invites/{code}` | Revoke an unused code |
| POST | `/api/admin/accounts/{uuid}/password` | Issue a new password, returned once; signs the account out |
| DELETE | `/api/admin/accounts/{uuid}` | Delete an account and its character |
| DELETE | `/api/admin/bridged/{uuid}` | Forget a bridged player, releasing their name |

## Configuration

Variables in `wrangler.jsonc`:

| Variable | Default | Description |
| --- | --- | --- |
| `SERVER_NAME` | `Ratatoskr` | Service name shown in the metadata document |
| `PUBLIC_URL` | empty | Public origin. When empty it is derived from the incoming request, which is usually correct |
| `SKIN_DOMAINS` | empty | Additional hosts permitted to serve textures, comma-separated. The service's own host is always included |
| `BRIDGE_UPSTREAMS` | empty | Other services whose players may join. See [Bridge mode](#bridge-mode) |

There is one secret, set by `setup`: `SIGNING_KEY`, an RSA private key in PKCS#8 PEM
form.

## Bridge mode

A Minecraft server can point authlib-injector at only one authentication service.
Bridge mode lets that service be this one while players keep using an account they
already have elsewhere — the official Mojang service, LittleSkin, or any other
authlib-injector compatible service:

```jsonc
"vars": { "BRIDGE_UPSTREAMS": "mojang, littleskin=https://littleskin.cn/api/yggdrasil" }
```

Entries are comma-separated: `mojang` for the official service, or `label=api-root`
for anything else, where the API root is the address a launcher would be given. The
label is stored against every player the upstream vouched for, so keep it stable if
the address changes. Leaving the variable empty, the default, turns bridge mode off.

Nothing changes for the Minecraft server — it is still started with
`-javaagent:authlib-injector.jar=https://<your-worker-url>/api/yggdrasil` — or for
players, who sign in with whichever launcher and account they already use.

How it works: when `hasJoined` finds no join record of ours, it asks the upstreams the
same question, all at once, and passes on the profile from whichever one recognises
the player. That profile is returned exactly as the upstream sent it, signatures
included.

**Names are protected.** A name belongs to whoever first joined with it:

- A character registered here always keeps its name. Nobody bridged can join as it.
- Otherwise, the first bridged player to join with a name holds it, identified by
  upstream and UUID. The same name from any other upstream, or from another UUID, is
  turned away, and registering it here is refused. A player who renames upstream
  carries their record over to the new name.
- An administrator can release a name from the administration view, under
  **Bridged players**, or with `DELETE /api/admin/bridged/{uuid}`.

Bridged players also resolve through `/api/profiles/minecraft` and
`/sessionserver/session/minecraft/profile/{uuid}`, so whitelists and bans work for
them, but only once they have joined at least once.

Things to know:

- **Chat signing.** On Minecraft 1.19.3 and later, a client signs in with a chat key
  from its own service, and the server checks that key against the keys it trusts:
  Mojang's, and this service's. Players from an upstream that issues its own keys —
  LittleSkin does (`feature.enable_profile_key`) — are disconnected moments after
  joining with *Invalid signature for profile public key*, whatever
  `enforce-secure-profile` says. Install a server-side mod that ignores chat keys,
  such as [No Chat Reports](https://modrinth.com/mod/no-chat-reports). Mojang players
  are unaffected.
- **Skins.** Skins from the official service display for everyone. A skin from
  another upstream carries that upstream's signature, which clients signed in here
  cannot verify, so they may show the default skin instead. The upstreams' skin
  domains are added to `skinDomains` so that the texture itself is not blocked.
- An upstream that is down or slow (over 5 seconds) is treated as not recognising
  the player, so the others keep working.

## Administration

The administrator is an ordinary account carrying an `is_admin` flag — the same
login, the same token, the same character in game. It is simply the account nobody
could have invited, which is why `setup` creates it directly instead of registering
it.

Signing in with it reveals an **Administration** section on the site:

- **Invite codes** — issue a code (optionally with a note recording who it is for),
  see which codes are still unused, revoke ones that have not been spent.
- **Accounts** — see every account and its character, issue a new password for one,
  or delete one.
- **Bridged players** — in bridge mode, see who has joined from another service and
  release a name.

Reissuing a password signs that account out everywhere and shows the new password
once. Deleting an account removes its character and frees the name. An administrator
cannot delete their own account, since on the last one that would leave nobody able
to administer the service.

The API behind the view is under `/api/admin`, authorised with the administrator's
ordinary Yggdrasil access token; there is no second kind of credential to manage.

### From the command line

Everything above also exists as a script, which is the way back in if the
administrator ever loses their password. Add `--local` to operate on the local
development database.

```bash
npm run invite                      # issue one code
npm run invite -- 5                 # issue five
npm run invite -- --note "for Bob"  # attach a reminder of who it was for
npm run invite -- --list            # every code, unused first
npm run invite -- --revoke <code>   # withdraw a code that has not been used
npm run reset-password -- Steve     # issue a new password for a character
npm run create-admin -- <email> <character-name>
```

To promote an existing account instead of creating a new one:

```bash
npx wrangler d1 execute ratatoskr --remote \
  --command "UPDATE users SET is_admin = 1 WHERE email_lower = 'someone@example.com';"
```

## Invites

Registration is closed except to whoever holds an invite code, and **a code is spent
by the account it creates**. Codes live in the database rather than in a secret, so
handing one out never grants more than one registration and no rotation is required.

A code is 16 characters of Crockford base32, grouped in fours
(`qmjb-cvbd-feyf-drbw`), which omits the letters `i`, `l`, `o` and `u` so that a code
can be read aloud without ambiguity. Only unused codes can be revoked: deleting a
spent one would allow it to be redeemed a second time.

## Passwords

**Users cannot choose their own password.** At registration the server generates a
random 20-character password of roughly 100 bits of entropy, formatted as
`k7rm-9xqt-2vhw-4pbd-6nzc`, and returns it exactly once in the registration
response.

This is a deliberate trade-off rather than an inconvenience for its own sake. A slow
key-derivation function such as PBKDF2 exists to compensate for the low entropy of
human-chosen passwords: guessing must be made expensive because the candidate space
is small. With a random 100-bit password the candidate space is 2¹⁰⁰, and an
attacker holding a leaked database cannot exhaust it regardless of how fast the hash
is. Passwords are therefore stored as a salted single-round SHA-256, which removes
the several milliseconds of CPU that a KDF would cost — the Workers free plan allows
only 10 ms of CPU per request — and halves the amount of code involved.

The cost is that a lost password cannot be recovered, only replaced. That is an
administrator's job — from the administration view, or from the command line:

```bash
npm run reset-password -- Steve
```

Either way the account is signed out everywhere and the new password is shown once.

> **Note**
> Adding a "choose your own password" or "change password" feature would require
> reinstating PBKDF2 at around 600,000 rounds. The argument above depends entirely
> on there being no path by which a weak password can be stored. Hashes are
> scheme-tagged (`sha256$…`), so both schemes can coexist and existing accounts
> would keep working. The invariant is documented at the top of `src/lib/crypto.ts`.

## Local development

```bash
npm run keygen > key.pem
printf 'SIGNING_KEY="%s"\n' "$(sed -z 's/\n/\\n/g' key.pem)" > .dev.vars
npm run migrate:local
npm run create-admin -- dev@example.com Dev --local
npm run dev
```

Sign in as that account to issue invite codes from the administration view, or run
`npm run invite -- --local`.

## Limitations

- One character per account. The schema allows for more; the API does not expose it.
- Removing a skin clears the reference on the character but leaves the image in KV.
  Because images are content-addressed, another character may still refer to the
  same bytes. This leaves orphaned data behind, in small quantities; a cleanup task
  can be added if it matters.
- The `/minecraftservices` endpoints — player certificates and chat signing — are
  not implemented, so servers must run with `enforce-secure-profile=false`.
- Error messages returned by the API are always in English, as the Yggdrasil
  protocol surfaces them directly to game clients. The web interface displays them
  as received.
